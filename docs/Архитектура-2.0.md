# Архитектура LAN Discovery 2.0

**Дата:** 01.10.2026 (PHASE 2.0-0)
**Вход:** `docs/Спецификация-2.0.md` (исходное ТЗ), фактический код LAN Discovery 1.1
(базовая линия `367b307` = тег `v1.1.0`+2).
**Правило №0 из спецификации:** сначала изучить код → определить границы →
найти готовые механизмы → отделить долг от необходимого → только потом
реализация. Этот документ — результат шагов 1–5; реализация — по `ROADMAP.md`.

---

## 1. Целевая модель

```text
Hardware
   ↓
Hardware Detection
   ↓
Capabilities
   ↓
Core Services
   ↓
Modules
   ↓
Roles
   ↓
UI / API / Automation
```

`Hardware ≠ Device Type`: одна и та же платформа может быть Network Gateway,
Home Server, Remote Site Appliance, Industrial Gateway, Diagnostic Box,
Camera/SDR Gateway, Backup Node, Media Server, Monitoring Node — функцию
задают capabilities + modules + role, а не модель железа.

Инварианты 2.0 (из спецификации, фиксируем как архитектурные законы):

1. **Не rewrite.** Рабочие части 1.1 переносятся, а не заменяются.
2. **Каждое крупное изменение — с техническим обоснованием** (в этом
   документе или в задаче фазы).
3. **Никаких абстракций ради красоты.** Core API появляется только там,
   где есть ≥1 реальный потребитель (модуль) и есть что абстрагировать.
4. **Логическая изоляция, не распределённость.** Один Python runtime;
   process isolation — только для нестабильных/опасных модулей.
5. **Capabilities — не True/False.** Только
   `present|absent|unknown` × `measured|detected|unverified` (уже так в 1.1).
6. **Долгая операция ≠ HTTP request.** Всё длинное — через Jobs.
7. **Опасная сетевая операция — транзакция**
   (Prepare→Apply→Verify→Commit, иначе Rollback) + предупреждение в UI.
8. **Модуль не делает голый subprocess/systemctl**, если есть Core API.

## 3. Gaps → необходимые изменения (обоснование по слоям)

Только то, что **нужно по спецификации** и не покрыто 1.1. Всё с привязкой
к фазе `ROADMAP.md`.

### 3.1 Capabilities 2.0 — углубление таксономии (PHASE 2.0-1)
- **Зачем:** спека §3 требует `network.*`, `storage.*`, `hardware.*`,
  `radio.*`, `camera.*`, `media.*`, `service.*`; сейчас — 4 группы.
  От capabilities зависят compat-check модулей и будущие роли
  (hardware_requirements) — без таксономии остальные слои строить не на чём.
- **Как:** расширить `collect()` в `core/capabilities.py`, сохранить
  формат записи и TTL-кэш; `GET /api/capabilities` — обратно совместимо
  (старые ключи не удаляем, новые добавляем); UI `/capabilities` — группировка
  по префиксам.
- **Не делать:** не вводить True/False, не вычислять «роль» из железа.
- **Реализовано (PHASE 2.0-1, 01.10.2026):** шесть групп добавлены в
  `collect()`; правила честности и семантика каждой пробы — в докстринге
  `core/capabilities.py`; `storage.local/removable/smart` подключены к
  compat-чекам манифестов без изменений `compute_status()`; тесты —
  `tests/unit/test_capabilities.py` (таксономия + monkeypatch-кейсы).

### 3.2 Core Services: границы + инвентаризация вызовов (PHASE 2.0-2)
- **Зачем:** спека §4 — убрать `Module → subprocess → Linux` в пользу
  `Module → Core API → subsystem → Linux`. 18 файлов со `subprocess` и
  13 с `systemctl` — это факт, который надо сначала описать, потом сокращать.
- **Как:** сначала **инвентаризация** (таблица вызовов: файл→роут→что
  делает→целевой core API→статус), затем фасады:
  - `core/services.py` — `status/start/stop/restart/enable/disable/logs/health`
    поверх systemd (спека §8, пример `services.status("transmission")`);
  - `core/process.py` — единственная точка безопасного запуска команд
    (timeout, capture, env, без shell где можно);
  - `core/config.py` — доступ к settings поверх `_cfg` (сейчас `_cfg` живёт
    в `app.py` — ядро не должно зависеть от app);
  - контракты `core/network.py`, `core/storage.py` — интерфейсы (read-only),
    реализация — в своих фазах.
- **Не делать:** не переписывать все 18 файлов разом; перенос — по одной
  функции за фазу, каждый перенос с тестом.
- **Реализовано (PHASE 2.0-2, 01.10.2026):** `core/process.py`,
  `core/services.py`, `core/config.py` + read-only-контракты
  `core/network.py`/`core/storage.py`; инвентаризация с планом переноса —
  `docs/Инвентаризация-core-2.0.md` (71 вызов в 13 файлах, точные
  цифры вместо «18/13» из первичного аудита); первый перенос — 5 точек
  (статус служб, роут управления службами, `/api/disks`, интерфейсы
  capabilities, чтение settings) с тестами `test_core_layer.py`;
  JSON-контракты роутов не менялись.

### 3.3 Jobs subsystem (PHASE 2.0-3)
- **Зачем:** спека §9 — «обязательный компонент»; сейчас `install_module`,
  backup/restore, scans живут внутри HTTP-запроса (зависание UI, таймауты,
  нет прогресса/логов/отмены).
- **Как:** `core/jobs.py` — manager + worker-треды; состояния
  `queued/running/completed/failed/cancelled`; запись
  `id/type/status/progress/started_at/finished_at/logs/result/error/cancelable`;
  хранение — sqlite (таблица `jobs`, рядом с events; retention как у events);
  `GET /api/jobs`, `POST /api/jobs/<id>/cancel`, виджет активных jobs в UI;
  первые миграции: module install/update, backup/restore БД, network scan.
- **Не делать:** не поднимать отдельный процесс/очередь (redis и т.п.) —
  в рамках разрешённой runtime-модели (спека §13).
- **Статус (02.10.2026):** реализовано в PHASE 2.0-3 — `core/jobs.py`
  (worker-пул, cooperative-отмена, sqlite `jobs`, retention/recover),
  роуты `/api/jobs` (+ `<id>`, cancel), виджет в `base.html`; мигрированы
  module install/catalog install+update, ручной network scan, db-backup.
  **db-restore остался синхронным**: `systemctl stop lan-discovery`
  внутри задачи убивает процесс-исполнитель — нужен внешний executor
  (решение отдельно). `GET /api/jobs/<id>` добавлен аддитивно сверх
  §5 (поллинг результата из JS).

### 3.4 Module system 2.0 + permissions + trust (PHASE 2.0-4)
- **Зачем:** спека §10–12. Манифест 1.1 — основа, но нет
  `capabilities/dependencies/conflicts/services/configuration/role_support`,
  нет `publisher/sha256/min_core_version/max_core_version`; catalog
  (`index → tar.gz → extract`) не проверяет checksum; `permissions` не
  показываются пользователю как запрос прав.
- **Как:** схема v2 поверх существующего STEP-8-подхода:
  старые манифесты валидны (нет полей → defaults, как сейчас с `version`),
  новые поля — контракт; сетка прав (`network.read/configure`,
  `storage.read/write`, `services.read/control`, `process.execute`,
  `camera.*`, `usb/gpio/serial.access`) — в манифесте и в UI установки
  («This module requires…»); catalog: SHA-256 из index на tarball,
  trusted sources в settings, `min_core_version` против `APP_VERSION`.
- **Не делать:** PKI/подписи — только фундамент (checksum+источник+версии);
  sandbox не обязателен (спека §11).
- **Статус (02.10.2026):** реализовано в PHASE 2.0-4 — `core/manifest.py`
  (сетка прав 12 ключей, `validate_manifest`, `core_version_ok`,
  `install_confirm_text`); `compute_status` проверяет min/max_core_version
  (→ incompatible), `capabilities` `group.key` (→ requires-hardware),
  модульные `dependencies` (→ requires-dependency); каталог проверяет
  SHA-256 из index (opt-in `require_sha256`), opt-in
  `trusted_publishers` (fail-closed), publisher index ↔ module.json, id
  манифеста, min/max_core_version до скачивания и после распаковки —
  результат в state (`entry.publisher`/`entry.sha256`); UI — confirm-запрос
  прав перед установкой + подписи прав в карточках. **sha256 — поле
  index.json, не module.json** (манифест не верифицирует сам себя).
  Schema-only (валидация без поведения, потребитель — Roles 2.0-5):
  `conflicts`, `services`, `configuration`, `role_support`; запрет
  одновременного включения conflicts и capabilities голыми группами не
  вводились. Тесты: `test_manifest_v2.py`, `test_module_catalog_trust.py`
  (35).

### 3.5 Roles 2.0 (PHASE 2.0-5)
- **Зачем:** спека §14 — роль ≠ «набор включённых модулей»: нужен manifest
  с required/optional/capabilities/hardware_requirements/conflicts/
  recommended_configuration/security_profile; профили сейчас зашиты в код.
- **Как:** `roles/<id>.json` в репо (как модули), загрузчик рядом с
  `core/roles.py`; compat-проверка — через существующий
  `compute_status()`/capabilities (где и живёт hardware-чек); примеры ролей
  из спеки (Gateway, Home Server, Remote Site, Industrial, Diagnostic,
  Camera — SDR ждём хвост спеки).
- **Не делать:** не ломать `POST /api/roles/<rid>/apply` и ALWAYS_ON.
- **Статус (02.10.2026):** реализовано в PHASE 2.0-5 — PROFILES удалён,
  роли живут в `roles/*.json` (9: legacy default/media/network + 6
  спека-ролей, SDR ждём хвост спеки); `validate_role`/`load_roles`
  (невалидные не показываются), `role_blockers` — роль с блокерами не
  применяется (`{ok:False, error}`), `_targets`: ALWAYS_ON > conflicts >
  членство; `roles_overview()` аддитивно расширен (required/optional/
  missing/not_installed/conflicts/blockers/ready/security_profile/
  recommended_configuration, `role` у модулей) — старые JSON-ключи 1.1
  сохранены, apply-роуты не менялись. Честность: `security_profile` и
  `recommended_configuration` — подсказки в UI (enforcement нет),
  обязательный список спеки целиком в `required_modules` (spека не
  разделяет — optional пуст до появления реальных модулей), у ролей
  capabilities только явные (rs485/ethernet). Тесты: `test_roles.py` (19).

### 3.6 Network Core + транзакции (PHASE 2.0-6)
- **Зачем:** спека §5–6 — самый опасный участок (риск отвязать сессию);
  сейчас операции — наборы shell-команд без verify/rollback.
- **Как:** `core/network.py`: объекты (interfaces/addresses/routes/firewall/
  …), транзакционный каркас Prepare→Apply→Verify→Commit/Rollback,
  UI-warning «This operation may disconnect the current session»,
  авто-rollback по таймауту/неверификации; DHCP/DNS/VPN/AP — по мере
  появления модулей-потребителей.
- **Не делать:** не вырезать sys-network до перехода на core API.
- **Статус (02.10.2026):** реализовано в PHASE 2.0-6 — read-only объекты
  `list_interfaces/list_addresses/list_routes` (iproute2 JSON; недоступный
  источник → None → unknown), перенос wifi-scan (`_parse_iw_scan`,
  контракт 1.1) и nettools → `core.process`; `Transaction` (Prepare-снимки
  → Apply+Verify пошагово → Commit; провал → обратный Rollback; шаг без
  rollback → `rolled_back: False`) + insurance `schedule_rollback(check_fn,
  grace)` — авто-rollback из daemon-треда (панель переживает потерю связи,
  цель — вернуть доступ). Операторы `set_address/del_address/
  set_route/del_route` с валидацией до транзакции; UI sys-network block —
  warning «This operation may disconnect the current session» + форма
  (admin); новые роуты `/api/network/info` и `/api/network/address`.
  Отложено по мере потребителей (обосновано): DHCP/DNS/VPN/AP/bridge;
  firewall — после проектирования модели nft; внешняя проверка
  доступности извне (нужен наблюдатель вне панели) — страховка
  проверяет стабильность конфига+link. Тесты: `test_network_core.py` (27).

### 3.7 Storage Core (PHASE 2.0-7)
- **Зачем:** спека §7 — модули (downloads/torrent/dlna/backup/camera/media/
  filemanager) не должны каждый изобретать модель хранения; сейчас пути
  размазаны по константам модулей.
- **Как:** `core/storage.py`: корни `/srv/media|/srv/data|/srv/backup`,
  disks/partitions/mounts/SMART (на основе `hdd_device()` + lsblk/smartctl,
  которые уже в `TOOL_PROBES`), shares/backup-targets как записи;

## 4. Технический долг vs «не трогать»

| Позиция | Статус | Решение для 2.0 |
|---|---|---|
| Werkzeug dev-сервер под root, HTTP без TLS | принят («root by design» до 01.01.2027, `docs/Безопасность.md`) | **не трогать** в 2.0 без новых триггеров (удалённый доступ/WAN/второй не-админ) |
| `Server: lan-discovery` без версий | закрыто (№66) | сохранить |
| context manager не везде, io/SMART не опрашивается | осознанный остаток | улучшать **в рамках** Storage Core (3.7), не как отдельный долг |
| SHA-256 user/guest в users.json | residual §8.6 (ленивый re-hash при входе) | остаётся на 1.1/2.0, пароли операторские |
| WAN-проброс/файрвол | residual §8.7 (не проверяется) | вне 2.0 (физический периметр) |
| Дрейф repo↔сервер | закрыт (№61+№67, ежедневная задача) | относится к 1.1 (2.0 не деплоится) |
| Двойное сканирование OP+X96 | закрыто (№59) | OP остаётся на 1.1 — **не подключать к 2.0** |
| Прямые `subprocess`/`systemctl` | долг, но рабочий | сокращать постепенно (3.2), не «большим взрывом» |

## 5. Правила совместимости 1.1 ↔ 2.0

1. **Два репозитория, одна история:** `Lan-discovery-2.0` создан клоном
   `Lan-discovery-1.1` (remote `upstream-11` сохранён) — cherry-pick
   горячих фиксов 1.1 → 2.0 и обратно.
2. **1.1 продолжает жить:** X96 (`192.168.3.243`) и Orange Pi работают на
   1.1; фиксы безопасности, нужные обеим версиям, — сначала в 1.1 (боевой),
   затем cherry-pick в 2.0. **2.0 на X96 не деплоится** до отдельного
   указания (будет свой префикс/устройство).
3. **API не ломаем:** новые поля/эндпоинты — аддитивно
   (`/api/capabilities` старые ключи остаются); удаление — только с
   миграцией UI.
4. **Манифесты/конфиги — back-compat:** старые `module.json` (v1) валидны
   без правок; v2-поля опциональны.
5. **Синхронизация:** `tools/sync_check.py` настраивается для 2.0 отдельно
   (когда появится деплой-цель); для 1.1 — ежедневная задача №67.
6. **Версия:** `APP_VERSION` репо 2.0 = `2.0.0` (Unreleased в CHANGELOG),
   тег `v2.0.0` — только на релиз (как `v1.0.0`/`v1.1.0`).

## 6. Целевые контракты core API (черновик, уточняется в фазах)

```python
# core/services.py (фаза 2.0-2)
services.status(name) -> {"state": ..., "active": bool, ...}
services.start/stop/restart(name) -> ok|error
```
