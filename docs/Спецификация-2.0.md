# LAN Discovery 2.0 — архитектурная эволюция в Universal Modular Appliance Platform

> **Статус:** исходная спецификация принята 01.10.2026 как входное ТЗ на версию 2.0.
> Хвост документа (SDR Gateway и разделы **§15–37**) получен 02.10.2026 и
> дописан ниже дословно. Производные документы: `docs/Архитектура-2.0.md`
> (анализ 1.1 и план перехода), `ROADMAP.md` (фазы 2.0),
> `docs/2.0/ARCHITECTURE_AUDIT.md` (аудит §37 Phase 0).

Ты работаешь непосредственно с репозиторием:

`kotmartovskiy/Lan-discovery-1.1`

Текущая версия проекта — LAN Discovery 1.1.

Твоя задача — **спроектировать и поэтапно подготовить LAN Discovery 2.0 как универсальную локальную Linux/ARM appliance-платформу**, сохранив рабочие части LAN Discovery 1.1 и не превращая проект в бессистемный rewrite.

## 0. Главное правило

НЕ начинай с полного переписывания проекта.

Сначала:

1. изучи фактический код репозитория;
2. определи реальные архитектурные границы;
3. найди существующие механизмы, которые уже можно использовать;
4. отдели технический долг от действительно необходимых изменений;
5. сформируй архитектуру 2.0;
6. только после этого начинай реализацию.

Любое крупное изменение должно иметь техническое обоснование.

Не создавай абстракции только ради красивой архитектуры.

# 1. Что должно стать LAN Discovery 2.0

LAN Discovery 1.1 уже является модульным appliance-приложением.

LAN Discovery 2.0 должен сделать следующий шаг:

**не просто LAN Discovery с модулями, а универсальная локальная appliance-платформа, где конкретная функция устройства определяется установленными возможностями, модулями и ролью.**

Целевая модель:

```text
Hardware
   ↓
Hardware Detection
   ↓
Capabilities
   ↓
Core Services
   ↓
Modules
   ↓
Roles
   ↓
UI / API / Automation
```

При этом:

```text
Hardware ≠ Device Type
```

Один и тот же компьютер должен иметь возможность работать как:

* Network Gateway
* Home Server
* Remote Site Appliance
* Industrial Gateway
* Network Diagnostic Box
* Camera Gateway
* SDR Gateway
* Backup Node
* Media Server
* Monitoring Node

без изменения базовой платформы.


Используй существующую систему capabilities из 1.1 как основу.


```text
measured
detected

```

Не заменяй это простой моделью `True/False`.

# 4. Core Services

В 2.0 необходимо постепенно убрать ситуацию:

```text
Module
   ↓
subprocess
   ↓
Linux
```

и прийти к:

```text
Module
   ↓
Core API
   ↓
System subsystem
   ↓
Linux
```

Создай архитектурные границы для:

```text
core.network
core.storage
core.services
core.security
core.process
core.jobs
core.firewall
core.config
core.events
core.hardware
core.discovery
```

Не обязательно реализовывать всё сразу.

Сначала определить API и постепенно переносить существующую функциональность.

# 5. Network Core

Это один из наиболее важных компонентов 2.0.

Network Core должен в перспективе управлять:

* interfaces
* addresses
* routes
* bridges
* VLAN
* NAT
* forwarding
* firewall
* DHCP
* DNS
* VPN
* Wi-Fi AP
* policy routing
* link state

Модули не должны напрямую менять networking, если для операции уже существует Core API.

Целевая схема:

```text
network-router
network-dhcp
network-dns
network-firewall
network-vpn
network-ap
network-bridge
        ↓
Core Network Manager
        ↓
Linux networking
```

---

# 6. Транзакционные изменения сети

Особенно опасные операции должны иметь модель:

```text
Prepare
   ↓
Apply
   ↓
Verify
   ↓
Commit
```

При ошибке:

```text
Rollback
```

Например изменение IP/маршрута/firewall/Wi-Fi/AP не должно просто выполнять несколько shell-команд без проверки результата.

UI должен предупреждать:

> This operation may disconnect the current session.

И по возможности поддерживать автоматический rollback.

Storage Core должен постепенно абстрагировать:

* disks
* partitions
* filesystems
* mounts
* mount points
* removable media
* SMART
* filesystem health
* storage pools
* shares
* backup targets

Модули типа:

```text
downloads
torrent
dlna
backup
camera
media
filemanager
```

не должны каждый самостоятельно изобретать свою модель storage.

Например:

```text

   ↓
/srv/media
/srv/data
/srv/backup
```

# 8. Services Core

Нужен единый интерфейс для управления системными сервисами:

```text
status
start
stop
restart
enable
disable
logs
health
```

Вместо того чтобы каждый модуль напрямую вызывал `systemctl`.

Например:

```python
services.status("transmission")
services.restart("lan-discovery")
```

Конкретная реализация может использовать systemd.

# 9. Jobs subsystem

Это обязательный компонент 2.0.

Любая долгая операция должна перестать выполняться непосредственно внутри HTTP request.

Примеры:

* apt install
* pip install
* module install
* module update
* backup
* restore
* disk scan
* SMART scan
* firmware update
* network scan
* large file operation
* system update
* role installation
* configuration migration

Целевая модель:

```text
UI/API
  ↓
Job Manager
  ↓
Background Worker
  ↓
Operation
```

Job должен иметь:

```text
id
type
status
progress
started_at
finished_at
logs
result
error
cancelable
```

Минимальные состояния:

```text
queued
running
completed
failed
cancelled
```

UI должен показывать активные jobs.

# 10. Module system 2.0

Существующие module loader/catalog использовать как основу.

Но module manifest постепенно должен описывать:

```json
{
  "id": "...",
  "version": "...",
  "description": "...",
  "capabilities": [],
  "dependencies": [],
  "conflicts": [],
  "permissions": [],
  "hardware": {},
  "services": [],
  "configuration": {},
  "role_support": []
}
```

Разделить:

```text
module metadata
module compatibility
module dependencies
module runtime
module permissions
module configuration
```

# 11. Module permissions

Модуль должен явно объявлять необходимые права.

Например:

```text
network.read
network.configure

storage.read
storage.write

services.read
services.control

process.execute

camera.read
camera.control

usb.access

gpio.access

serial.access
```

UI должен показывать пользователю:

> This module requires access to network configuration and system services.

Не предоставлять модулю больше прав, чем необходимо.

Полная sandboxing-модель пока НЕ обязательна.

Сначала реализуй permission model как архитектурный контракт.

# 12. Module security

Текущая модель установки:

```text
index
→ tar.gz
→ extract
→ install
```

должна постепенно перейти к более доверенной модели:

```text
Module
├── version
├── publisher
├── source
├── SHA-256
├── signature
├── min_core_version
└── max_core_version
```

Поддержать:

* checksum verification
* trusted sources
* publisher identity
* core compatibility
* module versioning

Не реализовывай сложную PKI только ради галочки.

Сначала сделай фундамент.

---

# 13. Runtime model

Важно:

LAN Discovery 2.0 НЕ обязан сразу превращать каждый модуль в отдельный процесс.

Допустима модель:

```text
Core
 +
Modules
```

в одном Python runtime.

Главная задача 2.0 — **логическая изоляция**, а не преждевременная распределённость.

Если модуль потенциально нестабилен или опасен, отдельно рассмотреть process isolation.

Текущая discovery-система хорошая, но IP не должен быть основной идентичностью устройства.

Целевая модель:

```text
device_id
    ↓
MAC
    ↓
hostname
    ↓
IP history
```

При необходимости использовать composite fingerprint.

Обеспечить корректную работу при:

* DHCP
* смене IP
* roaming
* VPN
* временном исчезновении
* MAC change
* нескольких интерфейсах

Не ломать существующую event-модель:

```text
NEW
ONLINE

MAC_CHANGED
```


# 26. Update / rollback

Разделить:

**Application rollback** — code, config, database, modules

и:

**System rollback** — apt, kernel, drivers, system packages, network

Не утверждать, что обычный application rollback откатывает всю ОС.

Для system-level changes предусмотреть:

```text
preflight
→ backup
→ apply
→ verify
→ rollback
```

# 34. Versioning

У проекта должен быть ОДИН источник версии.

Не должно быть ситуации:

```text
README = 2.0
app.py = 0.9
module = 1.x
```

Используй единый version source.

Модули имеют собственные версии.

Core имеет свою версию.

# 35. Definition of Done для архитектуры 2.0

LAN Discovery 2.0 можно считать архитектурно готовым, когда:

* Hardware отделён от Roles
* Capabilities являются главным механизмом hardware compatibility
* Core APIs определены
* Network subsystem централизован
* Storage subsystem централизован
* Services API существует
* Jobs существуют
* Module Manager использует Jobs
* Roles декларативные
* Events являются системным механизмом
* Module permissions определены
* Module versioning определён
* device identity не зависит только от IP
* installer поддерживает ARM/x86
* rollback явно разделяет application/system
* UI использует единый application shell
* Demo использует API abstraction
* есть appliance smoke test
* документация соответствует реальному коду
